# CIP-0001: Replace Theano and MPI with modern NumPy

## Status

- [x] Proposed - Initial idea documented (open for Discussion feedback)
- [x] Accepted - Phase 1 started on branch `cip0001-numpy-encoder` (regularisation: keep no-op + FutureWarning)
- [x] In Progress - Phase 3 (chunked psi-statistics) under way
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

PyDeepGP has two legacy compute dependencies: **Theano**, used for the MLP
encoder behind back-constrained models, and **MPI** (`mpi4py`), used for
data-parallel inference. Neither works on a current Python/NumPy stack:

- The **default model does not build**. `DeepGP(...)` defaults to
  `back_constraint=True`, which imports Theano. Theano is unmaintained, does
  not build on Python 3.13, and is not declared in `install_requires`, so
  `pip install` succeeds and construction then fails.
- The **MPI path crashes on NumPy ≥ 1.24** (`np.dtype(np.int)` in
  `util/parallel.py`), and with `back_constraint=False` it gives **silently
  wrong results**.

This CIP replaces the Theano encoder with a NumPy implementation (prototype
verified against the stored reference results), makes the MPI path correct
while deprecating it, and replaces its single-machine role with chunked,
optionally threaded psi-statistics in NumPy. Measured on a 2-core machine,
the NumPy replacement matches MPI's speed and uses far less memory. MPI is
removed after a deprecation window unless the Discussion finds multi-machine
users.

This is PyDeepGP's first CIP and adopts the VibeSafe / GPy CIP format
(see GPy `cip/`, e.g. CIP-0010).

**Prototype artefacts** (not yet a PR) live under [`cip/cip0001/`](cip0001/):
NumPy encoder + MPI `np.int` patch, and a monkey-patch sketch for
chunked/threaded RBF psi-statistics.

Community review: Discussion draft in [`cip/cip0001/discussion-draft.md`](cip0001/discussion-draft.md).

## Motivation

### Evidence (2026-11-13, `main` at `82089eb`)

**Theano encoder**

- `deepgp/encoder/mlp.py` imports Theano at module level. `DeepGP` and the
  layer classes use it whenever `back_constraint=True` (the default).
- Theano is not in `install_requires`. README: "Back-constraint encoder tests
  are skipped unless Theano is installed." Four reference tests
  (`DGP_BC_*` in `test_model_basic.py`) never run in CI.
- The encoder is a small dense MLP (tanh / softplus / linear layers); Theano
  is used only for its forward pass and backpropagation.
- Two latent bugs in the same file:
  - `raise 'Unsupported activation function!'` raises a string, which is
    itself a `TypeError` in Python 3.
  - When the gradient is supplied externally (the only way `MLP` is used,
    including `MLP_model`), the graph builds `cost = (external_grad*output).sum()`
    and drops `add_cost`, so the `regularization` / `reg_weight` options
    have no effect.

**MPI**

- `util/parallel.py` maps `np.dtype(np.int)`, removed in NumPy 1.24. Any
  `mpi_comm` use fails on current NumPy.
- After patching that line, the design is correct only for back-constrained
  models. `DeepGP.optimize` runs the optimiser on the root rank, and the
  `optimizer_array` setter broadcasts root's **entire** parameter vector. With
  `back_constraint=False`, the per-data-point latent variables on other ranks
  are overwritten with root's, giving a wrong objective (≈1% off in the test
  below) with no warning.
- MPI touches 9 modules (≈144 references): `util/parallel.py`,
  `inference/vardtc_parallel.py`, `inference/vardtc.py`,
  `inference/svi_vardtc.py`, `inference/svi_ratio.py`, `layers/layers.py`
  (`SparseGP_MPI`, the base class of every layer), `layers/enclayer.py`,
  `layers/mrd.py`, `models/model.py`. `.coveragerc` omits most of these.

**Where the time goes.** Profiling one objective-plus-gradient evaluation
(2 layers, N=2000, M=50) shows most of the time in GPy's RBF psi-statistics
(`__psi2computations`, `_psi2compDer`). These are already vectorised NumPy;
the cost is element-wise `exp` over N×M×M arrays, which NumPy runs
single-threaded. MPI helps by splitting N across processes, which also splits
the N×M×M memory.

### Prototype results

A prototype (separate working copy; not yet a PR) with (1) a NumPy `mlp.py`,
(2) `np.int` → `np.int64`, and (3) a chunked/threaded replacement for GPy's
RBF psi-statistics gives:

- **Encoder:** `checkgrad` passes for `MLP_model` with tanh, softplus and
  `positive_obs`; input gradient matches finite differences to 2e-10. With
  the Theano skip removed, **all 8 tests in `test_model_basic.py` pass**,
  including the four back-constrained reference tests (stored log-likelihoods
  at `rtol=1e-5`) that CI currently skips.
- **MPI (back-constrained):** 2 ranks agree with one process to ≈1e-9
  relative in objective and gradient.
- **Performance** (2-core Linux, OpenBLAS 1 thread, best of 3, one
  objective+gradient evaluation; chunk = 500 rows):

| N, M | NumPy, 1 process | Chunked, 1 thread | Chunked, 2 threads | MPI, 2 ranks |
|---|---|---|---|---|
| 2000, 50 | 220 ms, 430 MB | 299 ms, 197 MB | 152 ms, 227 MB | 107–125 ms, 290 MB/rank |
| 8000, 100 | 4.1–5.2 s, 4.0 GB | 4.1 s, 430 MB | 2.5 s, 590 MB | 2.7 s, 2.1 GB/rank |

Two MPI ranks and two threads give similar speed. Chunking keeps peak memory
roughly constant in N; MPI only divides it by the number of ranks. Giving
BLAS 2 threads instead was slower than 1 thread, as expected when time is in
element-wise operations. Thread scaling beyond 2 cores is **not yet measured**.

## Detailed Description

### Phase 1 — NumPy encoder (restores the default model)

| ID | File(s) | Rewrite |
|---|---|---|
| R1 | `deepgp/encoder/mlp.py` | Replace Theano with NumPy. Keep class names (`Layer`, `MLP`, `MLP_model`), parameter names (`layer_i.W`, `layer_i.b`), weight initialisation, the `X_center` handling, `positive_obs` softplus output, gradient accumulation between `prepare()` calls, and the `update_gradient(X, dL) → dL/dX` contract. Forward: cached pre-activations per layer. Backward: `dlin = dout * act'(lin)`, `dW += dlinᵀ h_in`, `db += Σ dlin`, `dout = dlin W`. Softplus via `np.logaddexp(0, x)`; its derivative via a numerically stable sigmoid. Replace `raise '…'` with `ValueError` at construction. |
| R2 | `deepgp/encoder/mlp.py` | **Regularisation:** decide (open question 1) between preserving the current no-op with a `FutureWarning` when `regularization` is set, or implementing L1/L2 correctly (a behaviour change for anyone passing it). |
| R3 | `deepgp/testing/test_model_basic.py` | Remove the `HAS_THEANO` skip so the four `DGP_BC_*` reference tests run in CI. |
| R4 | `deepgp/testing/` (new `test_encoder.py`) | `MLP_model.checkgrad()` for each activation and `positive_obs`; finite-difference test of the returned input gradient; clone round-trip. |
| R5 | `.coveragerc` | Stop omitting `deepgp/encoder/*` and `deepgp/layers/enclayer.py`. |
| R6 | `README.md`, `setup.py` / `pyproject.toml` | Remove Theano wording; no new runtime dependency. |
| R7 | `examples/*.py` | Run all three examples (they use back-constraint) as a smoke test. |

Phase 1 changes no results: the reference tests are the acceptance check.

### Phase 2 — Make MPI correct, then deprecate it

| ID | File(s) | Rewrite |
|---|---|---|
| R8 | `deepgp/util/parallel.py` | Remove the hand-written dtype map (`numpy_to_MPI_typemap`). mpi4py infers MPI datatypes from NumPy buffers, so `comm.Allreduce(arr, out)` etc. suffice. This fixes the `np.int` crash and shrinks the module. |
| R9 | `deepgp/models/model.py` (`DeepGP.__init__`) | If `mpi_comm` is given with `back_constraint=False` (or any layer has per-data-point trainable parameters), raise `ValueError` explaining the root-broadcast design. |
| R10 | all `mpi_comm` entry points | Emit `FutureWarning` when `mpi_comm` is not `None`: "MPI support is deprecated; use chunked psi-statistics (see CIP-0001)". |
| R11 | CI (optional job) | `mpiexec -n 2` test comparing 2-rank and 1-process objective/gradient for a back-constrained model (`mpich` + `mpi4py` from PyPI install without system MPI). Runs only while MPI exists. |

### Phase 3 — Single-machine replacement: chunked psi-statistics

The MPI algorithm in `VarDTC_parallel` is a map-reduce over data rows:
per-rank `psi0` (sum), `psi2` (sum), `psi1ᵀY` (sum) and `YRY` (sum) are
reduced; the M×M algebra runs once; per-row gradients (`dL_dpsi1`,
`dL_dpsi0`, `dL_dYmean`, `dL_dYvar`) are computed locally. The same structure
works over chunks within one process.

| ID | Where | Rewrite |
|---|---|---|
| R12 | **GPy** `kern/src/psi_comp/rbf_psi_comp.py` (and `linear_psi_comp.py`) | Add optional row-chunking (and a thread pool) to `psicomputations` / `psiDerivativecomputations`, using the existing pure `__psi*` / `_psi*compDer` functions (the prototype monkey-patches this seam). Sums for psi2 and parameter gradients; concatenation for psi1, `dL_dmu`, `dL_dS`. Configured by chunk size and thread count (defaults: off, so results are unchanged). Benefits GPy's Bayesian GPLVM as well. **GPy home:** backlog (or a small CIP) under [GPy CIP-0010](https://github.com/SheffieldML/GPy/blob/main/cip/cip0010.md) — single-machine scaling that reduces reliance on MPI, which CIP-0010 already lists as a deprecation candidate. |
| R13 | GPy psi cache | Keep psi1/psi2 caching per chunk so derivatives do not recompute them (the prototype's ~35% single-thread overhead at small N comes from cache misses). |
| R14 | `deepgp/inference/vardtc.py` | Restructure as an explicit map-reduce over row-chunks with a pluggable reducer (`sum` locally; `Allreduce` only while MPI exists). This makes one inference implementation serve serial, chunked and MPI cases, replacing the duplicated `vardtc.py` / `vardtc_parallel.py` (≈510 lines). Works for any kernel via the `kern.psi*` / `*_expectations` API (memory cap); threading is used only through R12's thread-safe pure functions. |
| R15 | `deepgp/inference/svi_vardtc.py` | Same map-reduce structure for the SVI path. |
| R16 | `DeepGP` / layer constructors | New options `psi_chunk_size=None`, `psi_threads=1` passed down to inference; documented in README. |

**Thread safety.** GPy kernels cache results (`Cache_this`) and write
`.gradient` in place, so calling `kern.psi1` etc. from several threads is not
safe. Threads run only inside the pure psi functions (R12); kernel-level
chunking in PyDeepGP (R14) is serial.

### Phase 4 — Remove MPI (after the deprecation window)

Unless the Discussion identifies multi-machine users (open question 2):

| ID | File(s) | Rewrite |
|---|---|---|
| R17 | `inference/vardtc_parallel.py`, `util/parallel.py` | Delete. |
| R18 | `layers/layers.py` | Rename `SparseGP_MPI` → `SparseGPLayer` (keep `SparseGP_MPI` as a deprecated alias); remove root-only branches for `Kuu_sigma`, KL terms and gradient reductions; remove `reduceArrays` calls for kernel, `Z` and `delta`. |
| R19 | `layers/enclayer.py` | Remove `_gather_gradients` and the parameter broadcast. |
| R20 | `layers/mrd.py` | Remove MPI arguments and branches. |
| R21 | `models/model.py` | Remove the `optimize` override, the `optimizer_array` setter override (root-broadcast loop), the `_IN_OPTIMIZATION_` flag and the `Gatherv` paths in data-collection helpers. |
| R22 | `inference/vardtc.py`, `svi_vardtc.py`, `svi_ratio.py` | Remove `mpi4py` imports and `mpi_comm` arguments. |
| R23 | Public signatures | Keep accepting `mpi_comm=None`, `mpi_root=0` for one further release; raise `TypeError` if `mpi_comm` is not `None`. |
| R24 | `.coveragerc`, README | Remove MPI omits and wording. |

If multi-machine use is confirmed, Phase 4 instead reduces MPI to the
pluggable reducer in R14, so the MPI-specific code shrinks to that one place.

### Non-goals

- Porting PyDeepGP to JAX / GPy2 (GPy CIP-0010 frames that; on JAX, sharding
  and `vmap` replace both chunking and MPI).
- Changing models, objectives or default hyperparameters.
- MRD and prediction-only SVI helpers beyond removing their MPI code (separate
  revival work; see README limitations).

### Alternatives considered

| Option | Verdict |
|---|---|
| NumPy encoder + chunked psi + deprecate MPI (this CIP) | Preferred |
| Pin to Theano / Aesara / PyTensor | PyTensor is maintained, but adds a heavy compiler dependency for a few dense layers; NumPy is enough |
| PyTorch or JAX encoder | New heavy dependency in a NumPy codebase; better left to a GPy2-era port |
| Fix MPI and keep it as the parallel strategy | Still crashes users who run without MPI; multiplies memory per rank; duplicated inference code |
| Do nothing | Default model stays broken on current Python |

## Implementation Plan

1. **Proposed:** open the Discussion (questions below).
2. **Phase 1** (one PR; no Discussion dependency except regularisation
   wording): R1, R3–R7, plus R2 per Accept decision.
3. **Phase 2** (small PR): R8–R11.
4. **Phase 3:** R12–R13 as a GPy PR (backlog under GPy CIP-0010), then
   R14–R16 in PyDeepGP; benchmarks on a many-core machine recorded here.
5. **Phase 4:** after at least one release carrying the R10 warning, R17–R24.

## Backward Compatibility

- **Phase 1:** restores behaviour; reference log-likelihoods unchanged. Saved
  models: encoder parameter names and shapes unchanged, so `param_array`
  values and HDF5 reference files load unchanged.
- **Phase 2:** R9 turns a silently wrong configuration into an error. R10 adds
  a warning only.
- **Phase 3:** new options default to current behaviour.
- **Phase 4:** removes MPI; `mpi_comm` arguments are accepted (as `None`) for
  one more release.

## Testing Strategy

- Reference-value tests (`dgp_*.h5`, `dgp_bc_*.h5`) run in CI for every
  phase, including the back-constrained tests that are skipped today.
- Encoder gradient tests (R4).
- Chunked vs unchunked equality for objective and gradients (multiple chunk
  sizes, including chunk size not dividing N), and `checkgrad` with chunking on.
- Optional MPI job (R11) until Phase 4.
- Benchmarks (time and peak RSS) for N ∈ {2000, 8000, 32000}, M ∈ {50, 100},
  threads ∈ {1, 2, 4, 8, …} on a many-core machine before Phase 4.

## Open questions (resolve at Accept)

1. **Encoder regularisation:** keep today's no-op (with a warning) or make
   L1/L2 work as documented?
2. **Multi-machine use:** does anyone run PyDeepGP across several machines with
   MPI? If yes, keep MPI as the R14 reducer hook; if no, remove it.
3. **Where chunking lives:** GPy psi functions (R12, thread-safe, RBF/linear
   only) plus PyDeepGP serial chunking (R14, any kernel) — or only one of them?
   Recommended default: do R12 in GPy first (shared win for Bayesian GPLVM);
   keep R14 as the PyDeepGP map-reduce that can use R12 when present.
4. **Deprecation window:** one PyDeepGP release, or aligned with GPy CIP-0010's
   window?
5. **Defaults:** once benchmarked on many-core machines, should chunking (and
   threads) be on by default above some N?

## Relationship to GPy CIP-0010

GPy CIP-0010 is the **GPy2 readiness** frame: deprecation policy, upgrade
contract, and a candidate list that already includes **MPI** (replace with
"sharding / other, if needed"). This PyDeepGP CIP does not replace CIP-0010.

- **Theano → NumPy encoder** is PyDeepGP-local (GPy never depended on Theano).
- **MPI fix / deprecate / remove** in PyDeepGP **aligns with** CIP-0010's MPI
  candidate: same direction, different package.
- **Chunked/threaded psi-statistics in GPy (R12)** is the natural "other" for
  single-machine scaling. It belongs in GPy because the hot path is
  `GPy.kern.src.psi_comp`, and Bayesian GPLVM benefits too. Treat it as work
  **under CIP-0010** (backlog item or a small focused GPy CIP that cites 0010),
  not as a detour from GPy2 readiness.
