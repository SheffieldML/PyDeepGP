# CIP-0003: Renovate and refactor PyDeepGP

## Status

- [x] Proposed - Initial idea documented (open for review)
- [x] Accepted - Approved 2026-11-27, with decisions below
- [x] In Progress - Phase 2 started 2026-11-27
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

This is an umbrella CIP. It sets the target shape of PyDeepGP after
renovation and orders the work. CIP-0001 (Theano/MPI removal) and CIP-0002
(MRD revival) are children of it; further children are created only when
this CIP is Accepted.

The target, in one paragraph: layer mathematics become pure array-in /
array-out functions; `DeepGP(GPy.Model)` and the layer classes remain as a
thin GPy-native shell over them; two inference families — **collapsed**
(the 2013 psi-statistic bound) and **uncollapsed / doubly stochastic**
(after GPc CIP-0035) — sit behind one layer interface; MPI and Theano
disappear; the useful workflow of the Matlab `deepGP` is recovered as
small tested features; and correctness is checked against recorded golden
values and against GPc through the shared JSON interchange.

## Motivation

> **Correction (2026-11-27).** The evidence below was gathered from a local
> `main` that was behind `origin/main`. Upstream already contains CIP-0001
> Phases 1–3 (NumPy encoder, MPI deprecation, chunked psi; PRs #37–#40) and
> CIP-0002 Phases A–C (MRD revival; PRs #42–#43), plus the Damianou 2013
> examples (#41, #44). The default model builds, and 53 tests pass on the
> synced `main` (GPy 1.15, NumPy 2.5). The remaining problems described
> below — MPI as the base class of every layer, duplicated VarDTC, no
> pure-function layer core — still stand. Phases 1 and most of Phase 3 are
> therefore done; the plan below is updated accordingly.

Three bodies of work now pull in different directions, and PyDeepGP is
the one that has not moved.

**Matlab `deepGP`** (Damianou & Lawrence, AISTATS 2013; `hsvargplvm*`)
defines the capabilities users remember: a collapsed variational bound
with a Bayesian GP-LVM at each layer, MRD multi-view leaves, ARD scale
inspection and pruning, SNR control, priors on parameters and parent
layers, initialisation options, layer sampling and posterior propagation.

**PyDeepGP today** (~3.2k lines) implements the same bound as GPy
`SparseGP` subclasses.

- The default model does not build: `back_constraint=True` imports Theano,
  which is not a declared dependency (CIP-0001).
- MPI is the base class of every layer (`SparseGP_MPI`) and fails on
  NumPy ≥ 1.24.
- MRD is advertised but fails in `initialize_parameter` (CIP-0002).
- VarDTC is duplicated locally (`vardtc.py`, `vardtc_parallel.py`,
  roughly 500 lines) rather than shared with GPy.

**GPc** now has a doubly stochastic deep GP (`CDeepGp`, CIP-0035) with
minibatches, Adam, natural gradients, non-Gaussian final likelihoods and
several inducing families (points, ridge windows, Hermite windows —
CIP-0037, CIP-003D), together with `CBayesGplvm`, `CMrd` and a JSON model
interchange (CIP-0016).

**GPy** is separating numerical functions from parameter objects
(CIP-000F), adding sparse linalg / LQ modes for VarDTC (CIP-0013), and
building a golden-value corpus and `to_dict` contract (CIP-0010).

If PyDeepGP stays as is, it falls further behind both neighbours, and it
cannot use the improvements either of them offers. Renovating it is
largely a matter of aligning it with changes that already exist.

### Tenets applied

- **GPy-native stack:** layers stay GPy models; we reuse GPy's VarDTC,
  SVGP and kernels rather than keeping local copies.
- **Layered composition:** depth is a stack of layers with a shared
  interface; inference is per-layer and pluggable.
- **Maintained core first:** the serial sparse-variational path sets the
  quality bar; MPI, Theano and prediction-layer clones do not.
- **Honest public surface:** anything advertised must run; otherwise it
  fails clearly.
- **Test what you ship:** each phase below closes only when CI exercises
  what it adds.

## Detailed Description

### Decisions taken (2026-11-27)

| Question | Decision |
|---|---|
| Numerical backend | Stay on NumPy/SciPy and GPy. Track GPy's JAX evaluation (CIP-0010 Workstream G); do not lead it. |
| Uncollapsed inference | Prototyped and lived in PyDeepGP first, then transferred to GPy once the layer API is proven (see Phase 4). |
| Matlab parity | Reproduce the paper's experiments and the workflow that matters. We do not port the Matlab code or follow its structure. |

### Target architecture

1. **Pure layer functions** (`deepgp/functional/`, name provisional).
   Bound, psi-statistic propagation and gradients as functions of arrays
   and hyperparameters, following the CIP-000F Stage 2 conventions. No
   `Param`, no observers, no communicator.
2. **GPy shell.** `DeepGP`, `ObservedLayer`, `HiddenLayer`,
   `TopHiddenLayer`, `ObservedMRDLayer` keep their names and constructor
   patterns. They hold parameters and call the functions.
3. **Inference families behind one interface.**
   - *Collapsed:* the 2013 bound. This is the default and the reference
     for Matlab comparison.
   - *Uncollapsed:* whitened `q(u)` per layer, reparameterised samples
     propagated through layers, minibatches and natural gradients. This
     follows GPc CIP-0035 and starts from GPy's SVGP core where it
     suffices.
   The per-layer interface needs: forward marginals at supplied inputs,
   accept upstream gradients, expose parameters. This is the same
   boundary GPc CIP-0035 found necessary for hidden layers.
4. **Encoder.** NumPy MLP (CIP-0001). Back-constraints stay optional.
5. **No MPI, no Theano.** Single-machine scale comes from chunked psi
   (CIP-0001) and minibatching (uncollapsed family).

### Matlab capabilities to recover

| Capability | Matlab | Priority |
|---|---|---|
| MRD multi-view layers | `demHighFive*` | High (CIP-0002) |
| ARD scale inspection and pruning | `ShowScales`, `PruneModel`, `RetainedScales` | High |
| Initialisation options for `X` | `InitXOptions` | High |
| Layer sampling, posterior propagation | `SampleLayer`, `PosteriorMeanVar` | Medium |
| SNR control | `ControlSNR`, `CheckSNR` | Medium |
| Priors on parameters / parent layers | `AddParamPrior`, `AddParentPrior` | Medium |
| Classification demo | `demHsvargplvmClassification` | Medium |
| Dynamics, mocap, skeleton display | `demSkelMult*`, `ShowSkel` | Deferred; visualisation falls to GPy CIP-000B |

Acceptance demonstrations are the toy, USPS and high-five experiments of
Damianou & Lawrence (2013), already scaffolded under
`examples/damianou2013/`.

### Verification

- **Golden corpus.** Extend the stored `.h5` references into a corpus
  with recorded tolerances, in the manner of GPy CIP-0010.
- **GPc cross-check.** Small identical models exchanged through the
  CIP-0016 JSON interchange; objectives and gradients compared between
  PyDeepGP and GPc. This is a stronger test than self-consistency.
- **Gradient checks** for every layer type and both inference families.

## Implementation Plan

Phases are ordered; each phase is a separate child CIP or PR set. No
backlog tasks are created until this CIP is Accepted.

1. **Phase 1 — Make the default model build.** CIP-0001: NumPy encoder,
   MPI deprecation, chunked psi, Theano-skipped tests running in CI.
2. **Phase 2 — Extract and unify.**
   - Extract pure layer functions.
   - Remove `SparseGP_MPI` as a base class.
   - Replace the local VarDTC copies with GPy's, including CIP-0013 modes.
   - Define the layer interface of the target architecture.
3. **Phase 3 — Recover multi-view and diagnostics.** CIP-0002 (MRD),
   then ARD scale inspection and pruning, then initialisation options.
4. **Phase 4 — Uncollapsed family in PyDeepGP.** Implement on the Phase 2
   layer interface using GPy SVGP where possible; reproduce GPc
   CIP-0035's reference numbers on shared small problems. Then open a
   GPy CIP proposing transfer of the layer-ready SVGP pieces.
5. **Phase 5 — Verification corpus.** Golden corpus and GPc interchange
   checks; wire into CI.
6. **Phase 6 — Remaining Matlab workflow.** Sampling, SNR control, priors,
   classification demo. Revisit GPy2 compatibility using the CIP-0010
   inventory.

## Backward Compatibility

- Class names, constructor patterns (`nDims`, kernel lists, `add_layer`)
  and the `predict` / `optimize` / `checkgrad` surface are kept.
- `mpi_comm` arguments follow the CIP-0001 deprecation window, then go.
- `gen_pred_model` / `gen_pred_layer` continue to raise
  `NotImplementedError` until PredLayer replacements exist.
- Saved models: current `.h5` / pickle behaviour is kept through Phase 2;
  a `to_dict` path arrives with Phase 5.

## Testing Strategy

Each phase closes only when CI covers what it adds (test-what-you-ship).
Coverage gating continues on the maintained path and widens as MRD and the
uncollapsed family enter it. Long optimisations stay in examples.

## Resolved Questions (2026-11-27)

1. **Does GPy's SVGP expose the hidden-layer boundary? No; Phase 4 needs a
   small core of our own.** From reading `GPy/core/svgp.py` and
   `inference/latent_function_inference/svgp.py`:
   - `q(u)` is unwhitened, parameterised by `q_u_mean` and a Cholesky of
     its covariance. The KL needs `Kmm⁻¹`, and there are no natural
     gradients. GPc CIP-0035 found whitening necessary for stacking.
   - The bound is hard-wired to `likelihood.variational_expectations`. A
     hidden layer's "likelihood" is the rest of the network, so it must
     accept upstream gradients `(dL/dμ, dL/dv)` instead.
   - Inputs are fixed data. The marginals `(μ, v)` at supplied inputs are
     computed inside `inference()` and not returned. Input gradients are
     recoverable (`dL_dKmn` and `dL_dKdiag` are in `grad_dict`, and
     `kern.gradients_X` / `gradients_X_diag` exist), but `SVGP` does not
     assemble them.
   - Minibatching uses `climin` with internal slicer state, not a seeded
     generator we control.
   What is reusable: GPy kernels, `Posterior`, `choleskies`, the mean
   function hooks. The new core is a pure function computing whitened
   marginals and KL, which is the thing worth proposing to GPy
   (CIP-000F Stage 2 style) at transfer time.
2. **Pure-function package: public.** Decided 2026-11-27. It is still
   marked provisional until Phase 4 settles its signatures.
3. **GPc interchange for deep models: not ready.** The gp-scuderia schema
   is a flat single-GP document (`type`, `kernel`, `inducing_inputs`,
   `likelihood`, `data`); `vi` is reserved but unimplemented, and
   CIP-0001 there excludes multi-layer and latent-variable models from
   0.1. Raised as gp-scuderia CIP-0006 with four Proposed backlog tasks
   (latent `q(X)` block, MRD, uncollapsed `deep_gp` with frozen `eps`,
   collapsed bound). Phase 5 here depends on it.
